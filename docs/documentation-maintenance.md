# 文档维护约定

> 范围：本仓库自有指南。仅在新增/整理文档时读取，不是每次编码必读。

## 阅读结构

```text
根 AGENTS -> 目标项目 AGENTS/开发指南 -> 当前任务专题 -> 代码与测试
```

UI 任务加读目标项目 PRODUCT/DESIGN；历史研究和发布记录仅在追溯时读。
同一规则只有一个详细维护位置，其他入口给短摘要与相对链接。

## 文件职责

| 文档 | 应写什么 | 不应写什么 |
| --- | --- | --- |
| 根 `AGENTS.md` | 项目路由、共享边界、风险与验证原则 | 各产品全部功能 |
| 子项目 `AGENTS.md` | 硬约束、任务到规范/代码的路由、测试入口 | 逐版本更新日志、完整操作流程 |
| `README.md` / 用户指南 | 用户如何开始、能做什么、常见操作与详细入口 | 反射字段全集、长实现计划 |
| `PRODUCT.md` | 用户、目标、平台和能力边界 | 随版本追加细节 |
| `DESIGN.md` | token、布局、组件、状态反馈与可访问性 | 服务算法、完整写入协议 |
| 功能专题 | 数据契约、流程、异常、安全条件、代码/测试入口 | 跨域无关细节、重复通用 UI token |
| 带日期的研究/验证 | 当时环境、证据、限制、已做/未做 | 无日期的当前结论、默认执行命令 |
| Release/Update Notes | 发布历史/当前升级摘要 | 开发规范 |

保留工具需要的 PRODUCT schema 和 DESIGN frontmatter，不为精简破坏机器读取格式。
第三方工具文档、许可证与已完成历史计划不裁剪正文；只通过索引/状态说明降低误读。
不修改 `release/`、`dist/` 等生成目录内的文档副本。

## 写法

- 入口建议控制在 40-100 行；这是维护目标，不是删掉安全约束的硬上限。
- 专题直接写“触发条件 -> 操作 -> 不变量 -> 失败处理”，用表格区分不同策略。
  例如小窗、完整分镜、LevelSequence、Excel 的保存行为不能合成“全部自动保存”。
- 新规则先找既有专题；只有独立职责且现有文件难以容纳时才新建文件并补路由。
- 文档状态明确为现行、计划、研究或历史；混合文件在章节级标状态。
- 版本从 `VERSION` / `package.json` / `APP_VERSION` 定位，不在每个索引重复固化。
  日期写清是结构核对、静态核对还是运行验证，不能只改日期冒充重新验收。
- 源码实现与已发布 EXE 分开；后台接口、前端接入、真实验收、打包发布分开。
- 代码位置引用文件和符号，不复制易漂移行号；命令注明工作目录、前置条件与副作用。
- 下载模型、写 UE/Excel、远端同步或发布命令不得混在普通回归测试里。
- 文档冲突先对照最新源码、测试与用户要求；不能为迎合旧指南回退已有功能。

## 修改检查

1. 读取目标文件最新内容与 diff，保留其他人正在写入的规则。
2. 更新规则所属专题；只有产品范围/UI/用户操作/跨域边界变化才同步相应入口。
3. 检查被缩写段落的每条安全条件仍在新位置可找到，不用归档代替现行约束。
4. 检查相对路径、锚点、代码文件与命令存在，代码围栏闭合。
5. 运行 `git diff --check`；纯文档不启动 UE/Excel、不触发写探针或全量业务测试。
6. 发布与提交需另行授权。当前部分发布工作流用 `目录/**` 匹配，子项目 Markdown
   推送到 main 也可能发布，不能假定“只是文档就没有发布副作用”。
