日期：2026-09-05

## 审查范围

本仓库包含四个独立桌面产品：

| 项目 | 设计入口 | 详细事实来源 |
| --- | --- | --- |
| SVNmate | `PRODUCT.md`、`DESIGN.md` | `README.md`、`README_svn_auto_tool.md`、`svn_auto_tool.py` |
| MigrationGuard | `migration_guard/PRODUCT.md`、`migration_guard/DESIGN.md` | `docs/migration-guard-requirements.md`、`docs/migration-guard-design.md` |
| ConfigLinker | `config_id_lookup/PRODUCT.md`、`config_id_lookup/DESIGN.md` | `config_id_lookup/README.md`、`USER_GUIDE.md`、`docs/README.md` |
| 镜头沙盘 | `dialogue-shot-sandbox/PRODUCT.md`、`dialogue-shot-sandbox/DESIGN.md` | `README.md`、`AGENTS.md`、`docs/README.md`、`src/styles.css` |

专题文档继续作为细节来源，不与视觉设计系统争夺入口。

## 1. SVNmate

### 执行进度

- [x] `distill`：音乐与托盘保留为高频图标，保存、日志、指南、更新和退出进入
  顶部“更多”菜单。
- [x] `layout`：工具模块收敛为“名称/版本状态 + 主动作 + 更多菜单”的固定单行。
- [x] `harden`：增加 Tooltip、`Alt+M` / `Alt+H` / `Alt+A` / `Ctrl+S`、
  首次托盘提示、完整模块路径入口和跨 DPI 最小窗口尺寸更新。
- [x] `polish`：主题色板与 ttk 样式抽到 `svnmate_theme.py`，并增加独立的
  成功、部分完成、失败与跳过摘要。

### 当前优势

- 主任务、工作目录、执行设置、工具模块和日志的区域边界清楚。
- 浅色/深色主题具有完整语义映射，并已有 Per-Monitor DPI 适配。
- 批处理状态、日志和失败恢复都是真实系统状态，不是装饰性反馈。

### 主要问题

1. **P1 - 顶部命令层级过平。** `音乐开`、`隐藏到托盘`、状态和`立即执行`同时占据
   主标题栏。音乐和托盘属于低频辅助动作，却与核心执行命令拥有相似可见性。
2. **P1 - 工具模块行的操作密度偏高。** 每行同时展示安装/打开、检查/更新、选择和
   Kindle 联动，状态变化会增加扫读成本。
3. **P2 - 主题 token 与组件样式仍内嵌在主类。** 视觉系统存在，但复用和审查需要
   阅读 `svn_auto_tool.py` 的大段实现。
4. **P2 - 完成状态仍较依赖整块日志变绿。** 对色觉差异用户，应把最终结果、失败数
   和恢复动作写成固定状态摘要。

### 下一步

1. [已完成] `/impeccable distill`：顶部只保留状态、两个图标、高频主动作和
   “更多”菜单。
2. [已完成] `/impeccable layout`：模块行使用固定主动作与行级菜单。
3. [已完成] `/impeccable harden`：补齐键盘入口、Tooltip、长路径访问、
   部分失败摘要和 DPI 切换处理。
4. [已完成] `/impeccable polish`：主题 token 与 ttk 样式已移入独立模块。

## 2. MigrationGuard

### 执行进度

- [x] `distill` 第一阶段：路线合并为单一摘要与覆盖菜单；主筛选压缩为
  “全部/待处理/已完成/阻断”，细分状态进入“更多”。
- [x] 扫描范围全部未选时按单据自动推导模块与 externals。
- [x] 无工作区自动刷新默认调整为 2 分钟，保留 5 分钟选项。
- [ ] 下一阶段：`clarify`，统一术语并显示动作禁用原因。

### 当前优势

- 单一粘贴区、自动单号解析和源/目标路线联动符合高频批量工作流。
- 文件表是界面主体，右侧证据详情与底部进度反馈方向正确。
- 完成、待处理、失败使用绿/橙/红，并保留文字状态。
- OB 两阶段门禁和提交后复核具有明确产品差异。

### 主要问题

1. **P1 - 路线与命令区仍有重复控制。** 源/目标各有按钮和下拉菜单，自动联动已经
   存在后仍要求用户理解两组控件。应显示一个“国内 trunk -> 海外 trunk/OB”路线
   摘要，手动覆盖进入低频菜单。
2. **P1 - 状态筛选一行包含 8 个选项和 8 个独立计数。** 这超过单个决策点的四项
   工作记忆范围。应优先显示“全部/待处理/已完成/阻断”，其余状态进入二级筛选。
3. **P2 - `920x640` 实现下限非常紧。** 文档已经统一为该实现值，但仍需要确认
   8 类状态筛选、长路径和右侧详情在 100%/150% DPI 下都可操作。
4. **P2 - 表格颜色角色过多。** 同一张表同时承载文件状态、Jira 阶段、路线和远端
   阶段颜色，用户需要反复解释颜色。状态列应使用图标+短标签，其他列降低色彩权重。
5. **P2 - “更新/迁移/复核”的前置条件不够可视。** 主按钮禁用时应就地说明缺少
   单号、工作区、UE、映射还是上一阶段复核。

### 下一步

1. [已完成] `/impeccable distill`：合并路线控制和状态筛选，保留自动推断结果与
   手动覆盖入口。
2. 运行 `/impeccable clarify`：统一“扫描/复核/刷新”“海外 OB/OSOB”等术语，并为
   禁用动作提供具体原因。
3. 运行 `/impeccable layout`：验证当前 920x640 实现下限，并重点检查 150% DPI、
   长路径和 8 类状态计数。
4. 运行 `/impeccable harden`：覆盖缓存回退、部分 Jira 失败、IPC 版本不兼容、
   取消提交和第二阶段中止状态。
5. 运行 `/impeccable polish`：抽取主题 token，减少散落在 `app.py` 的颜色和字体。

## 3. ConfigLinker

### 当前优势

- 关系查询、反向追踪、查询中心切换和历史回退形成了清晰的专家工作流。
- 浅色/暗色主题已经集中在 `config_linker/theme.py`，比其他 Tkinter 项目更易维护。
- 长路径、ID、坐标和旋转均以快速复制为目标。
- 在线角色资料和武器图标失败时不会阻断本地查询。

### 主要问题

1. **P2 - 24px 产品标题对紧凑工具偏大。** 标题与多组 9px 元数据形成跨度过大的
   层级，压缩了查询和结果空间。
2. **P2 - 在线同步、应用更新与数据加载都使用状态色/红点。** 三类状态应有不同
   位置与文案，避免把“有新版本”误读为数据错误。
3. **P2 - 关系卡片容易继续膨胀。** 角色资料和武器关系增加后，应坚持一级关系容器，
   不为每条记录叠加小卡片。

初版范围失真和角色/武器现行合同缺失已在本轮处理：旧计划标记为历史，当前行为
集中到 `PRODUCT.md`、`DESIGN.md`、README 和用户指南。

### 下一步

1. 运行 `/impeccable clarify`：统一角色/武器模式、搜索类型、多义命中、同步缓存和
   更新提示的文案。
2. 运行 `/impeccable layout`：压缩产品标题，把模式切换、返回、输入和搜索固定为
   单行；对角色三段关系与武器 4:6 分栏分别验收。
3. 运行 `/impeccable distill`：把低频同步、目录和更新入口收进设置菜单，保持结果区
   最大化。
4. 运行 `/impeccable harden`：验证超长中文名、重复 ID、1000+ 关联、断网图片、
   旧缓存和 96/120/144 DPI。
5. 运行 `/impeccable polish`：让角色、武器和档案窗口只消费 `theme.py` 的语义
   token，清除局部重复色值。

## 4. 镜头沙盘

### 当前优势

- 视觉方向非常具体，能清楚区分工程壳层、信号黄、空间青色与业务角色色。
- 工作区状态保持、长任务不中断、高风险写入复核和减少动态效果规则完整。
- Three.js 视口、镜头语言与 UE 导出不是装饰，而是产品核心交互。
- 桌面平台边界明确，不会被通用移动端建议误导。

### Impeccable 检测结果

对 `dialogue-shot-sandbox/src` 的确定性检测共得到 791 条：

- 10 条 warning：9 条侧边强调条、1 条通用字体提示。
- 781 条 advisory：539 条颜色未纳入 `DESIGN.md`、197 条字号不在 token 阶梯、
  44 条圆角不在 token 阶梯、1 条网格背景提示。

其中侧边信号条和镜头视口网格属于已确认的产品视觉语言，不应机械删除；真正的问题
是实现没有把这些例外收敛为命名组件和 token。`src/styles.css` 约 9970 行，包含
361 个不同的六位十六进制色值，而根 token 只有少量语义色。

规范写明正文不小于 11px、次级元数据不小于 8px，但 CSS 中有 247 处
`7px-10px` 字号声明，其中 2 处为 7px。这里同时存在真实可读性风险和规范漂移。

### 复核结论与第一轮执行

- 字号、token 和动效建议成立，但检测数量不能直接等同于缺陷数量。8-10px
  的坐标、ID、路径、状态徽标和微标签符合桌面高密度工具需求，应按角色保留。
- 实际存在三处 7px 可读文本，其中一处使用 `font` 简写而未被原统计计入；
  角色标签、工作区英文类别和检查器摘要均提升到 8px。
- 根字体移除未随应用分发的 `Space Grotesk`，统一以 Windows 原生
  `Segoe UI / Microsoft YaHei UI` 为界面字体；技术数据继续使用
  `Cascadia Code / Consolas`。
- CSS 已建立字号、圆角和核心动效语义 token，并优先迁移任务目标物、NPC 注册、
  导出确认和 NPC 迁移中的关键可读文本。全量颜色替换与 CSS 文件拆分暂缓，
  避免在缺少逐工作区视觉基线时扩大回归面。
- 第一轮后类型检测从 197 条字号 advisory 收敛为 25 条；剩余项主要是
  13/15/16/17px 的历史标题和控件尺寸，将在对应工作区重排时处理。大编号
  窄体回退栈收口为命名 token 后，原字体 warning 不再误报。
- 主工作区切换从 720ms 缩短为 480ms；减少动态效果模式同时立即清理旧工作区
  状态，不再只缩短 CSS 动画。
- 侧边信号条、启动页网格、业务角色色和大编号窄体字体均为现行设计明确允许的
  视觉语言，不按检测告警删除。

### 主要问题

1. **P0 - 字号规范与实现冲突。** 大量 8-10px 文本可能在 Windows 125%/150%、
   Chromium 缩放和中文混排下难以辨认；必须逐组件区分“装饰刻度”与“可读文本”。
2. **P1 - 颜色系统未被代码真正消费。** 361 个独立色值使状态、主题和对比度无法
   集中治理，新增工作区很容易产生近似但不一致的灰、绿、橙和蓝。
3. **P1 - 单个全局样式文件已成为设计债务中心。** 近万行 CSS 同时管理壳层、四个
   工作区、模态层、3D 视口和多轮主题覆盖，级联优先级正在替代组件边界。
4. **P1 - 一套 `DESIGN.md` 承担了过多表面策略。** 分镜工作台、NPC 迁移、任务目标物
   和导出审核的模式与风险不同，应分别拥有 surface brief，而非继续扩大全局规范。
5. **P2 - 720ms 工作区转场对操作型工具偏慢。** 保留方向感的同时，应验证连续切换、
   后台任务和减少动态效果下是否拖慢专家操作。

### 下一步

1. [第一轮已完成] `/impeccable typeset`：建立 8/9/10/11/12/14/18px 的明确
   用途，清除可读文本中的 7px，并优先提升高风险确认与阻断说明。
2. [第一轮已完成] `/impeccable extract`：先建立字体、字号、圆角和核心动效
   token；中性色阶、状态色阶与按组件拆分 CSS 留待后续分批迁移。
3. 运行 `/impeccable distill`：逐工作区消除重复状态、重复标题和二次滚动，不改变
   分镜数据与 UE 写入控制点。
4. 运行 `/impeccable adapt`：只针对 Windows 桌面尺寸、DPI、配置小窗和
   `prefers-reduced-motion`，不做移动端改版。
5. 运行 `/impeccable harden`：覆盖长 NPC 名、12 人场景、无音频附件、UE 长时间
   加载、脏资产和超长路径。
6. 运行 `/impeccable polish`：用 Playwright 同批检查主要桌面视口和 Canvas 像素，
   再修复一次并停止。

## 推荐执行顺序

1. 镜头沙盘：`typeset -> extract -> distill -> harden -> polish`
2. MigrationGuard：`distill -> clarify -> layout -> harden -> polish`
3. ConfigLinker：`clarify -> layout -> distill -> harden -> polish`
4. SVNmate：`distill -> layout -> harden -> polish`

优先级按当前设计债务和用户风险排序。镜头沙盘需要先治理 token 与字号；另外三个
Tkinter 工具先压缩命令层级和状态复杂度，再统一样式实现。
