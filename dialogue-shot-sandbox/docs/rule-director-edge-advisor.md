# 规则导演端侧顾问

> 文档状态：现行专题规范
>
> 最近核对：2026-09-22（端侧分阶段更新）。

## 定位

端侧模型是规则导演内部的可选顾问，不是独立导演模式。规则导演始终拥有最终结果：

```text
立即显示纯规则基线
→ 端侧模型分析连续叙事节拍与台词问题
→ 规则系统按覆盖需求分段，立即显示节拍方案
→ 几何系统为每个镜头生成多个合法摄影机候选
→ 端侧模型逐镜、逐候选单图评分
→ 程序按结构化分数排序并选择机位
→ 组合结果再次通过全序列关系轴与投影验收
→ 镜头结果先显示，另行请求配乐建议
```

模型不得修改台词覆盖、角色进出场和站位，也不能输出摄影机 XYZ 坐标。模型离线、
超时或输出非法时，规则导演直接保留本地基线，不显示错误，也不阻断工作。
加载对话 ID、读取 Blueprint、回读已有镜头和进入配置小窗均不得启动模型；
只有用户明确点击规则导演或“评估已有分镜”后才创建推理租约。
已有镜头评估后的“生成调整建议”也是独立的显式推理入口。

当前输入包含对白、上下文、角色资料、BP 站位、朝向、Mesh 包围盒体型，以及
每个镜头的离屏 RGB 候选画面。候选画面采用与沙盘一致的体型代理、摄影机参数、
角色朝向和 21:9 安全框；模型只评分和排序，不生成坐标。

Depth 与 Instance ID 尚未接入，因此当前能够判断画面可读性和代理遮挡，但不等于
对 UE 最终网格、材质、动画姿态和真实场景遮挡的像素验收。

## 默认模型

默认使用 Ollama 中的 `qwen3-vl:4b`：

- 约 4.4B 总参数；
- Q4 Ollama 包约 3.3GB；
- 支持文本、图片、多图和视频；
- 当前同时用于叙事节拍分析和规则候选画面评分。

正式安装包默认不携带 Ollama 或模型权重。普通用户可在“设置与更新”的
“端侧导演模型”一行查看状态：

- 未安装 Ollama 时，点击“安装 Ollama”打开官方 Windows 安装页；
- Ollama 已安装但模型缺失时，点击“下载模型”，应用通过 `/api/pull` 下载并
  显示实时进度；
- 模型已安装时，第一次端侧分析会按需启动本机服务，无需配置端口；应用启动
  本身不会占用模型内存。

下载模型不是使用基础规则导演的前置条件。开发者也可以手动准备：

```powershell
ollama pull qwen3-vl:4b
npm run advisor:start
```

`advisor:start` 只检查本地模型并启动已有 Ollama，不会自行下载。

## 可替换模型

顾问支持 Ollama 原生 API 和 OpenAI-compatible API，可替换为其他 Qwen、
Gemma 或内部微调模型：

```powershell
$env:RULE_ADVISOR_API_STYLE = "ollama"
$env:RULE_ADVISOR_BASE_URL = "http://127.0.0.1:11434"
$env:RULE_ADVISOR_MODEL = "qwen3-vl:4b"
npm run dev
```

配置项：

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| `RULE_ADVISOR_ENABLED` | `1` | 设为 `0` 完全关闭端侧顾问 |
| `RULE_ADVISOR_API_STYLE` | `ollama` | `ollama` 或 `openai` |
| `RULE_ADVISOR_BASE_URL` | `http://127.0.0.1:11434` | 推理 API 根地址 |
| `RULE_ADVISOR_MODEL` | `qwen3-vl:4b` | 可替换模型 ID |
| `RULE_ADVISOR_API_KEY` | 空 | 可选网关鉴权 |
| `RULE_ADVISOR_TIMEOUT_MS` | `60000` | 单次建议超时 |
| `RULE_ADVISOR_MAX_TOKENS` | `1024` | 建议输出上限 |
| `RULE_ADVISOR_CONTEXT_TOKENS` | `8192` | Ollama 上下文长度 |
| `RULE_ADVISOR_MODEL_IDLE_MS` | `60000` | 最后一次推理结束后卸载模型的等待时间 |
| `RULE_ADVISOR_RUNTIME_IDLE_MS` | `600000` | 应用托管 Ollama 的空闲退出时间 |
| `RULE_ADVISOR_TEMPERATURE` | `0.1` | 生成温度 |
| `RULE_ADVISOR_RESPONSE_FORMAT` | 空 | 服务支持时设为 `json_object` |

`ollama` 模式使用原生 `/api/chat`，可关闭 thinking 并控制上下文；替换为
vLLM、SGLang 或其他兼容服务时，将 `RULE_ADVISOR_API_STYLE` 设为 `openai`，
并把 `RULE_ADVISOR_BASE_URL` 指向其 `/v1` 根地址。

## 状态检查

启动镜头沙盒后：

```powershell
Invoke-RestMethod http://127.0.0.1:5173/api/rule-advisor/status
```

状态接口返回启用状态、连通性、API 地址和当前模型，不返回 API Key。

使用内置示例对话执行完整协议联调：

```powershell
npm run advisor:smoke
```

Vite 不在默认 `5173` 端口时，先设置
`RULE_ADVISOR_SMOKE_URL` 为实际的 `/api/rule-advisor/analyze` 地址。

## 节拍协议

第一阶段返回 `rule-beat.v1`。每个节拍必须连续覆盖对白，并包含叙事功能、强度、
覆盖策略和可选强调角色。可用覆盖策略包括保持关系镜头、普通主体、反应、强调和
重新建立空间。

同一响应可通过 `dialogue_issues` 标注明确影响理解、上下文连续、角色口吻、信息
重复、叙事节奏或因果逻辑的台词问题。每项必须绑定当前对白节点，并区分“建议复核”
与“建议修改”；模型只输出原因和修改方向，不自动改写或保存原台词。没有可靠问题
时返回空数组。节拍阶段完成后，这些标注会立即显示在当前对白条和导演检查器，不
等待后续视觉候选全部评分完成。

配乐使用独立 `/api/rule-advisor/music` 请求，返回 `request_id` 与 `music_cues`，
不再把音乐目录放入节拍提示词。镜头结果显示后才读取已加载的音乐目录；目录等待、
音乐推理失败均不阻断已有镜头。请求会携带最多 256 项真实音乐
目录，以及当前对白节点从 UE 回读的已有音乐状态。每项建议只能引用当前对白 ID
和目录内 `state_id`；每个节点最多一项，重复节点、目录外状态以及与 UE 当前状态
相同的建议会被过滤。普通寒暄、现有配乐已经合适或没有可靠目录匹配时必须返回
空数组，不使用启发式规则自动补一首音乐，也不把前一节点建议显示为当前节点
“沿用中”。

节拍与镜头不是一一对应：相邻节拍的覆盖类型、主体、交流对象和视觉需求相同时，
可以共用镜头；叙事标签或强度改变本身不切镜。覆盖需求改变或要求重建空间时保留
切点，短镜合并不能吞掉这个变化。角色进出场、时长和停顿继续参与原有分段规则；
一个节拍也可跨多个镜头。合并镜头保留各节拍理由的摘要，遵守输出协议的 240 字符
限制；完整理由仍在原节拍建议中。

`rule-beat.v1` 新增两个可选字段，旧响应仍兼容：

| 字段 | 含义与执行 |
| --- | --- |
| `interaction_target_slot` | 当前主体所看或交流的对白角色；必须在场且不是主体自身。反应镜头可明确指定引发反应者 |
| `visual_motivation` | `{kind, dialogue_id, evidence}`；节点属于本节拍，依据逐字引用该节点原文，执行时还须落在当前镜头内 |

单人或带群主体覆盖默认静态、常规视线空间。`reveal`（具体揭示）和 `realization`
（认知转变）允许轻微推近；`isolation`（孤立或抽离）允许拉远并留空；
`entrapment`（受阻或受困）只启用压迫留白，不自动推近。保持关系及重建空间仍使用
稳定全景。强度继续用于分析展示及既有焦段选择，不直接控制运动或压迫留白。
没有动机、引用不存在或不在当前镜头内时保持默认；引用校验只证明原文存在，
不能证明模型对其含义的理解正确。

未给出有效交流对象时，反应镜头先找当前段落中的说话者，其余情况优先识别句首
明确称呼，再参考最近交流者与后续发言者。只有唯一其他角色时才直接采用；多人
关系不明时保留群体中心，不再选角色列表里的第一个人。纯规则基线中的感叹号、
追问和强调词也不再自动触发推近或压迫留白。模型始终不能输出摄影机坐标。

## 视觉选优协议

第二阶段返回 `rule-camera-ranking.v1`。几何系统先为每个镜头求解最多三个互不
重复的摄影机位置；候选只有在当前安全框、景别、遮挡、关系轴和运动投影验收不
引入新失败时才标为合法。每份评分包含：

- 从 0 开始的 `shot_index`；
- 稳定的 `candidate_id` 与候选标签；
- 是否为规则基线；
- 四项视觉分数、综合分、可见问题和一句取舍判断；
- 每个镜头的完整候选排序与选中候选。

视觉评分包含：

- 构图稳定性 `composition`；
- 主体可读性 `subject_readability`；
- 遮挡质量 `occlusion`；
- 相邻镜头连续性 `continuity`；
- 综合分 `overall`；
- 最多四项可见问题 `issues`。

软件不再抽取四个代表镜头。每个镜头都至少生成一个画面，并按镜头顺序、候选顺序
逐张调用 VLM；模型从不在一次请求中同时观看多张图，因此不会混淆镜头或候选
索引。推理耗时随“镜头数 × 合法候选数”线性增长。任何一张评分失败时，本次
视觉选优无效并保留规则基线；节拍分析结果仍可独立参与。

VLM 排序完成后，程序按排名逐项尝试候选。若首选机位与前面已选机位组合后破坏
关系轴或投影合法性，则自动尝试下一名；最终镜头检查器显示实际采用的候选、分数
和原因。左侧导演控制区同步显示候选生成与逐张评分进度。

## 分阶段更新、缓存与取消

- 纯规则基线不等待音乐目录；节拍建议完成后立即更新镜头和台词标注，视觉评分
  随后选优。无视觉结果时保留节拍方案；音乐只更新建议，不重新应用镜头。
- 左侧“停止分析”保留已显示方案。新设计、对白或镜头数据改变、开始编辑对白、
  切换工作区、进入配置小窗会取消当前端侧请求。请求号与 AbortSignal 共同阻止
  晚到响应回写。TRAE 切回规则时继续保留原有后台协作任务。
- 生成链路按镜头让出主线程；取消会在下一个批次前生效。单个镜头的同步几何
  求解不能在中途抢占。离屏渲染共享一个上下文，完成、失败和取消均释放资源。
- 服务端在客户端断开后中止模型 HTTP 请求；不再把取消当作“模型不可用”继续
  生成。已经开始的远端偏好查询与运行时启动可能先结束，但不会再启动后续推理。
- 生成流程使用进程内 LRU 推理缓存：最多 256 项，15 分钟 TTL，不持久化业务数据
  或图片。键包含实际提示词（含相关偏好）、响应 Schema、图片和模型/API 设置；
  节拍、音乐提示词不包含随机请求号，返回时绑定本次请求号。
- 只缓存解析与业务引用校验通过的结果，失败/取消不缓存。命中不启动模型运行时；
  `force_regenerate: true` 绕过命中。已有分镜评估/调整建议仍每次重新评分。
- 当前未缓存几何求解或候选图片；重复任务仍会渲染以校验实际画面依赖。缓存
  降低重复推理次数，不构成对实际加速倍数、显存下降或画面质量的保证。

## 已有分镜评估

读取 BP 与 UE 镜头后，可主动点击“评估已有分镜”。此流程不生成候选、不调整
镜头、不写 UE；复用投影规则、代理画面渲染、逐图评分与模型运行时。

- 规则检查先返回，区分未通过和建议；已有配置没有声明的目标景别、构图与主体
  意图不能从规则生成方案借用。发言角色仅作为参考，反应镜头等由人工复核。
- 只有角色均有 BP 站位才发送模型画面；站位缺失时提供参考规则检查，提示重新
  读取有效 BP。每镜发送原机位起始帧，保留 BP 朝向，不使用生成方案的转身。
- 模型返回构图、主体、遮挡、连续性、综合分与具体建议；连续性结合上一镜参数
  和对白推断，不代表看过完整运镜、动画或真实 UE 场景。
- 左侧显示进度与视觉均分，导演检查器按当前镜头显示分数和规则/模型反馈。
  模型失败或响应错配时保留规则结果，不显示伪造分数。
- 可以停止；切换对白、重读 BP、进入配置小窗或开始新设计时取消评估并清空
  旧结果。普通切镜不重新推理。此流程不读取或写入远端经验库。
- 独立入口为 `/api/rule-advisor/review`，请求校验真实镜头与画面的一一对应，
  不用新生成方案的镜头语义 Schema 限制已有配置。客户端中断会停止服务端推理。

### 已有镜头调整建议

逐镜评估下方可主动点击“生成调整建议”。复用几何求解器生成最多两个候选，
以当前发言角色作参考，保留原镜头可见角色；不从模型输出中读取坐标。
候选保持原对白覆盖、时长、焦距、横滚和运镜起止位移，只调整机位与取景方向。
检查全序列投影和前后切点，不引入新的硬失败、越轴、跳切或运动终点问题；
另对所表达的运镜路径采样检查代理投影，不等于 UE 动画验收。

- `/api/rule-advisor/review` 的 `suggest_existing` 请求只为目标镜头发送原画面与
  一至两个合法候选，并提供对白上下文、上一镜参数和原反馈。模型逐图评分；
  原画面也在本轮重新打分，界面明确显示“本轮比较”。
- 只推荐综合分高于本轮原镜头的候选；无改善、无合法候选、渲染失败、模型
  不可用或评分错配时明确说明，不自动修改镜头。
- “预览调整方案 / 返回原镜头”只切换中央视口，标题标记“建议预览 · 尚未采纳”。
  “采纳到草稿”再检查当前镜头身份与全序列问题后应用；“保留原镜头”不改数据。
- 采纳后可撤销本次采纳。采纳/撤销会使旧评估失效，需显式重新评估；每次生成
  只处理当前镜头，不隐式修改其余镜头的机位。
- 切换对白、重读站位、镜头数据变化或进入其他导演流程使未采纳建议失效，
  中止未完成请求。普通切镜不触发新推理，晚到响应不能覆盖新数据。
- 采纳仅进入当前会话的本地分镜草稿，不写 UE、不记录远端偏好；
  UE 写入仍由现有导出范围、差异审核和最终确认完成。

## 经验与偏好

两类经验分别存放在“分镜设计数据集”Base：

- `镜头返修案例库`：技术失败、修改前后和验收结果；只有已审核且通过或改善的
  案例会参与视觉返修。
- `导演偏好反馈库`：用户明确采用、拒绝、手动修改或方案选择；同一镜头使用稳定
  指纹更新，避免相互冲突的重复样本。

节拍分析会读取相关偏好；视觉候选评分会同时读取偏好与返修案例。飞书不可用时仅跳过
经验检索，不阻断本地导演。偏好表可通过 `DIRECTOR_PREFERENCE_TABLE_ID` 替换，
设定 `DIRECTOR_PREFERENCE_LIBRARY_DISABLED=1` 可完全关闭。

## 为什么模型不输出坐标

模型负责表达摄影意图，几何系统负责坐标。直接采用模型生成的 XYZ 会产生四类问题：

- 坐标依赖 UE 世界原点、角色局部轴、单位、槽位缩放和当前姿态，语言模型容易混用
  坐标系；
- 相同焦段、景别和构图对应连续的多组合法位置，单个坐标没有稳定语义；
- 遮挡、安全框、视线空间和运动路径需要投影或搜索才能验证；
- 直接坐标难以复现、缓存和随角色真实体型变化重新求解。

因此节拍模型只输出叙事功能和覆盖意图，确定性系统据此生成摄影机坐标候选；
视觉模型观看候选画面并排序，不直接产生或修改坐标。最终选择始终经过几何验收。

## 桌面封装

Electron 正式客户端已内置顾问 bridge。只有端侧分析或模型下载开始时才探测、
启动本机 Ollama；最后一个推理租约结束后显式卸载模型，持续空闲时再关闭应用
托管的运行时。默认地址由软件管理，普通用户不需要配置端口。开发模式与桌面
模式使用同一协议。

真正把推理运行时和约 3.3GB 模型权重放入安装包也可行：将 `ollama.exe` 作为
`extraResources/tools/ollama/ollama.exe`，将模型目录指向应用资源或首次运行数据
目录即可。当前发布采用设置页按需下载，不默认捆绑模型，原因是：

- 主程序每次更新都会携带大模型时，增量更新成本过高；
- GPU/CPU 运行时与模型权重应能独立升级；
- 模型许可证、签名和杀毒软件扫描需要单独处理。

推荐发布为“应用 + 受管 sidecar”：用户感知上仍是一个软件、无需端口配置，但
运行时和模型可以独立安装与更新。`RULE_ADVISOR_RUNTIME_PATH` 已允许桌面端指定
内置或自定义 Ollama 可执行文件。

## TRAE 局部精修交接

规则与端侧生成的每镜保留对应 `directorDecision`，局部精修以当前实际机位、
几何反馈和该镜 VLM 结论交接给 TRAE。提交时停止当前端侧优化并固定基线；
TRAE 仅返回选中镜头的语义决策，仍由本地求解和投影检查决定是否可采纳。
不重新发送候选图片或全量音频目录，具体版本与取消规则见
[分镜工作流](storyboard-workflow.md#当前镜头局部精修)。
