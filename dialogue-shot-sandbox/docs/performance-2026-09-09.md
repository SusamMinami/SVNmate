# 小窗性能与可靠性检查

日期：2026-09-09。基于 v0.24.3 发布前工作区；对照基线来自 v0.24.2。
本次未发布安装包，也未关闭或替换正在运行的已安装应用。

## 结论

小窗卸载视口，不等于退出 Chromium。Electron 主进程、渲染进程、GPU
进程和网络进程仍然存在；整库对白、编辑草稿、当前分镜和已加载模块也仍有
生命周期。因此，“超过 200 MB”本身不能证明内存泄漏，也不能承诺仅靠小窗
把整组进程稳定压到 200 MB 以下。

本轮不修改 CSS、分辨率、抗锯齿、角色几何、镜头规则、轮询间隔和 UE
写入审核。保留现有草稿和工作区功能。

## 已实施

| 位置 | 原有开销 | 本次处理 |
| --- | --- | --- |
| `src/App.tsx` | StageView 静态导入，桌面加载真实数据前会短暂挂载演示场景 | 视口动态加载；已配置数据目录的桌面启动等待真实数据，不初始化临时演示 Canvas；浏览器演示和首次设置仍保留 |
| `src/director/orchestrator.ts` | 候选离屏渲染器随主入口加载 | 有候选且确实需要评分时才导入；不减少候选或评分镜头 |
| `src/data/csvLoader.ts`、`csv.worker.ts` | 主页面读取并解析 HTTP JSON，然后把全量 CSV 字符串复制到 Worker | 配置读取、JSON 解码和文件文本读取全部放到 Worker；主页面只传读取指令或 File 对象，接收最终数据库 |
| `src/data/databaseIndex.ts` | 精确 ID 查询也会为整库构造全文搜索对象和小写文本 | 首次全文搜索才建立该索引；重复搜索复用，数据库替换后独立重建 |
| `server/ue/transport.ts` | 每个 TCP 分包都重新拼接已累积响应 | 读取 4 字节包头后按长度分配一次缓冲区；分段填充，支持拆包、粘包和连续响应 |
| Worker 和 TCP 生命周期 | 异常路径可能继续保留工作资源，关闭连接依赖对端结束 | Worker 成功、失败、克隆异常和 120 秒超时统一清理；TCP 主动关闭、超时、超限释放响应缓冲和全部等待者 |

Worker 超时仅涉及本地配置读取/解析，不是 UE 写入超时。不重试写入请求，
也不把 TCP 断开当作 UE 事务回滚。

## 测量结果

### 生产前端

使用生产构建、无扩展的 Edge headless、1440×900 桌面视口、50,000 条
合成对白。独立 HTTP 服务只提供构建文件和模拟响应，绝不访问真实 UE、
飞书或配置目录。完成数据加载后进入小窗，并通过 CDP GC 观察保留堆。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 主入口 JS，未压缩 | 1,545.31 kB | 985.23 kB |
| 实际加载脚本，未压缩 | 1,570,638 B | 1,011,188 B |
| 小窗渲染器 JS 保留堆 | 26.04 MiB | 23.70 MiB |
| 100 ms 采样到的渲染器 JS 堆峰值 | 28.15 MiB | 25.77 MiB |
| 小窗 Canvas 数量 | 0 | 0 |
| 页面运行异常 | 0 | 0 |

保留堆下降约 9%，启动加载脚本下降约 36%。修改后该桌面启动路径没有请求
StageView 模块。CSS 产物保持 `index-Dwl6BrUp.css`，样式未变。

限制：

- JS 堆不包含 Worker、原生对象、GPU、网络和 Electron 主进程内存；
  不能把这些数字当作安装版任务管理器总内存。
- 峰值是采样值，可能漏掉很短的分配峰值；不是全进程峰值。
- 合成对白用于固定实验条件，不代表用户真实数据的语言、长度和资产规模。
- 首次真正打开 3D 后，已导入的模块不会自动卸载；小窗释放 Canvas/场景
  资源，但引擎和驱动可能保留可复用内存。
- 本次验证不是长时间泄漏证明，仍需真实工程的持续使用采样。

复测命令：

```powershell
npm run build
node scripts/measure-performance.mjs current --check
```

脚本输出在 `artifacts/performance/`，不被普通 E2E 清理。
`PERF_ROWS` 可覆盖模拟行数。`--check` 会检查该路径未加载 StageView；
对比旧实现时不传该参数。

### TCP 微基准

同机将一个 8 MiB 响应分为 16 KiB 数据包，比较旧累计拼接算法与实际
`UnrealMcpConnection.consume`：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 累计复制量 | 约 2,060 MiB | 约 8 MiB |
| 单次本机组装耗时 | 393.5 ms | 2.4 ms |

这是合成响应组装基准，不包含 UE 操作、网络等待和 JSON 解析，不代表整个
资源读取流程同比加速。新增单测约束大响应接收期间不再调用累计 `Buffer.concat`。

### 已安装进程只读快照

检查时发现四个已安装应用进程，无 Ollama 进程。一个瞬时快照如下：

| 进程 | 工作集 MiB | Private Bytes MiB |
| --- | ---: | ---: |
| 主进程 | 32.6 | 117.3 |
| 渲染进程 | 20.6 | 82.1 |
| GPU 进程 | 23.7 | 208.3 |
| 网络进程 | 16.8 | 14.0 |

工作集和 Private Bytes 是不同口径；Private Bytes 不是当前驻留物理内存，
GPU 进程的 Private Bytes 也不等于显存用量。该快照不能否定用户此前
观察到的 200 MB，也不是修改前后的桌面包对照。

- 全量 Vitest：392/392，通过。
- 新增 16 项：TCP 6 项、CSV Worker 所有权/清理 7 项、延迟索引 3 项。
- 桌面 Playwright：40/40，通过，含镜头/俯视 Canvas 非空与运动验证、
  小窗节点同步、动作草稿、CSV 目录导入、音频和导出流程。
- 前端和 Electron 主进程/preload 构建通过；Impeccable 针对修改的 App
  检查无新增发现。
- 测试范围的缺陷分析未产生可证实的数据正确性缺陷；性能回归约束独立记录。
- 单测辅助工具在 Windows 报 `unsupported OS (cygwin)`，`utree flush`
  因工具未安装而失败；上述验证使用项目自带 Vitest，结果不依赖该工具。

## 后续优先级

1. **整库驻留和主线程索引。** 当前最终数据库仍完整保留在渲染器，首次精确
   查询也会构建多种索引。数据量很大时，下一步应测量各表/索引尺寸，再考虑
   将数据库留在 Worker，按对话/任务返回切片。需同步修改搜索、配表和工作区
   读取契约，不能只清空数据库。
2. **冷场景快照与草稿。** `useSceneReference.ts` 的 records 和
   `useCharacterActionEditor.ts` 的草稿 Map 随访问的对话累积。建议使用磁盘
   持久化加有限内存缓存，并支持失败恢复；直接按 LRU 删除草稿会改变现有功能。
3. **任务历史全量读取。** `storyboardTaskStore.ts:readAllTasks` 每次顺序读取
   并解析全部历史任务 JSON。任务很多时，改为轻量摘要索引、按需读取正文和
   明确的归档策略，避免状态检查加载所有历史分镜。
4. **多个 WebGL 上下文。** 主视口和缩略图各有 Canvas。后续可评估共享
   renderer/scissor 分区，但必须验证裁切、相机、标签、鼠标坐标和模态预览，
   不能为了内存牺牲现有画面。
5. **崩溃恢复与诊断。** 优先补充草稿自动保存和带进程分类的性能诊断，
   再考虑崩溃后重载。仅自动重启渲染器会丢失未保存状态。
6. **UE 本身的阻塞。** 所有回读/保存都还受 UE 主线程和插件响应影响。
   不应以更高频轮询或自动重试写入来掩盖延迟；保持阶段进度、超时说明和
   明确的重新预检机制。

不采用定时强制 GC、清空 Windows 工作集、关闭 GPU 加速或关闭安全隔离：
这些做法可能只改变数字、把开销转移到 CPU/换页，或降低可靠性。
