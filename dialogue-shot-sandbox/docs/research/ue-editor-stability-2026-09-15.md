# UE 编辑器崩溃调查与减负方案

> 2026-09-15，基于本机已有 UE 日志、当前源码和隔离浏览器验证。
> 这是调查记录，不代表已修复 UE 原生崩溃，也不是自动执行的改造清单。
> 未启动 UE 写探针，未改动 UE 资产、插件或已安装程序。

## 结论

近期崩溃不是单一问题。已有两份日志直接证明 MCP 在 UE 不允许的对象生命周期
阶段执行了操作；另有多次 Niagara/VectorVM 崩溃和较早的 Slate/对话编辑器崩溃，
不能仅因沙盒同时开启就认定同因。重复读取会增加风险暴露，但不是全部崩溃的解释。

## 沙盒中的风险放大点

- `src/app/useUeDialogueSelection.ts`：小窗持续调用 UE。请求完成后调度下一轮，
  但仅连续离线时退避；慢响应后最低只间隔 250 ms。退出仅取消后续计时和结果应用，
  不能取消已经进入 UE 的请求。
- `server/ue/dialogueSelection.ts`：选择读取有私有串行队列，但没有跨业务操作的
  排他边界；失败后会尝试通用图选择回退。空选择、API 不支持与连接异常需要区分。
- `server/ue/transport.ts`：超时关闭 socket 能防止串包，不证明 UE 已停止脚本。
  新连接继续发命令和客户端自动重试可能增加尚未结束的工作。
- `server/ueBridge.ts` 的 `readExistingDialogueStoryboard`：即使只读一个节点，
  仍先导出整段对话资产再筛选。节点少不等于 UE 内部工作量小。
- 原动作缓存以整组 ID 数组为键，`[A]` 与 `[A,B,...]` 不能共享；返回工作台会
  重读 A。原镜头配置读取标记退出小窗即清空，也增加往返读取。

## 优先改造

### P0：UE 插件入口保护，尚未实现

这是 E1/E2 的关键修复层，不能用 JavaScript 或 Python 异常捕获代替：

1. 在解析 UObject/类路径、反射查找、`ProcessEvent`、Python 执行之前做原生检查。
   核对当前引擎版本的 GC、保存、对象加载/PostLoad、退出与 World 切换状态；
   要么返回结构化 busy，要么推迟到安全 tick，并设置排队截止时间。
2. 调度必须在正确线程且允许执行的阶段。只投递 `AsyncTask(GameThread)` 不足以
   保证安全，主线程嵌套等待/资源加载也可能泵任务队列。需要防重入与执行深度保护。
3. 选择查询在同一次安全调用中返回纯数据：资产路径、真实节点 ID、编辑器/World
   会话版本；关闭编辑器、换图、LoadWorld 时使旧版本失效。避免跨多次往返持有
   节点路径并继续反射。
4. 写入依然实时核对选择、资产版本和审核凭证。客户端缓存只能做展示，不能放宽
   dirty、差异确认、回读与恢复约束。

本机 SeriaDialogEditor 没有 C++ 源码；OmniMcpCore 虽有 Source 目录，本次未找到
可修改的 `.cpp/.h`。因此未擅自替换 DLL 或声称修复原生入口。

### P1：沙盒请求治理，除缓存外尚未实现

- 使用覆盖整个业务操作的 UE 串行调度；选择轮询低优先级、合并重复读取，不让后台
  轮询插入写入/回读/保存。单进程队列不保护其他客户端，插件仍需统一调度。
- 搜索、LoadWorld、保存、编译期间暂停轮询。需要原生生命周期通知或安全的 busy
  返回值；再发一条普通 Python “查询是否忙”同样可能在入口崩溃。
- 超时/断连进入熔断状态，暂停自动追读，不自动重放写入；明确提示执行结果未知，
  再连接后按版本重新验证。关闭 HTTP 或 TCP 不等于取消 UE 操作。
- 逐节点增量读取、同目标 in-flight 请求合并、有限缓存。最终用原生节点快照 API
  替代每次整资产文本导出，减少跨调用反射和重复加载。

### P1：Niagara 与编辑器原生缺陷单独定位

先保留 dump、CrashContext 和匹配 PDB。由引擎/特效负责人检查出错 VM 指令、
Emitter/System、Data Interface 实例与预览 World 的释放顺序，再在授权测试副本上
做同场景的启停特效对照。不要先全局关闭 Niagara、强制 GC 或销毁预览 World。
Slate/SeriaDialogEditor 同样需要检查标签页关闭、搜索跳转和 shared-pointer 所有权。

## 本次已实现：跨模式节点缓存

- 动作/视线按节点保存，空结果也缓存；小窗返回工作台保留已读内容，仅请求缺失
  节点，复用角色 Montage 目录。补读期间已读节点不清空。
- 写入成功更新相应节点缓存，不再留下“单节点版本新、整组版本旧”的分裂副本。
- 镜头/音频配置读标记跨窗口模式保留；写入只失效目标节点，不连带清除其他节点。
  手动重新读取、换数据源/对话和离开工作区仍按边界失效。
- 本地对白本来就在同一 App 状态中保留；没有为窗口切换重新加载 CSV、Formation
  或运行导演。单节点配置摘要不是全量机位坐标，不能直接替代完整 BP/分镜读取。

独立回归：`e2e/dialogue-cache-handoff.spec.ts`。模拟响应的前后对照：

| 步骤 | 修改前 | 修改后 |
| --- | --- | --- |
| 小窗首次读取 | 读取 204801 + 角色目录 | 相同 |
| 返回工作台 | 读取 204801-204807 | 只读取 204802-204807 |
| 再回小窗 | 镜头配置标记已清空 | 复用已读镜头配置和动作 |
| 未读节点正在补读 | 原单节点动作被清空 | 已读动作仍显示 |

此结果证明重复读取减少，不证明 UE 原生崩溃已消除。测试响应完全模拟，
没有在真实 UE 中实施资产写入。正式安装包尚未更新。

本次验证：522 项单元测试、10 项桌面 E2E 均通过；`npm run build` 通过，
仍有既有的大 chunk 警告。E2E 覆盖缓存往返、空节点、补读期间保留已有数据、
显式刷新、选择同步、动作/视线写入和预设机位。已检查桌面截图。

## 临时使用建议

在 UE 搜索、加载场景/预览、编译或保存前退出小窗，让已有请求结束。
出现超时或断连先停操作，确认 UE 状态后再恢复，避免连续点击读取/写入。
这只能减轻风险；不得承诺退出小窗即可避免 Niagara 或编辑器自身的崩溃。
