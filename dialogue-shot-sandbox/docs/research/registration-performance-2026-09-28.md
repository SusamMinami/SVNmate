# NPC 注册、任务目标物与小窗性能核对

> 2026-09-28 源码实施与受控验证记录。不是安装包发布记录，也不是 UE 崩溃修复证明。
> 现行规则归 [NPC 注册](../npc-registration.md)、[任务目标物](../mission-target-preview.md)
> 与 [节点配置](../node-configuration.md)。

## 首轮变化（续作结果见文末）

| Before | After | Why |
| --- | --- | --- |
| NPC 注册与目标物操作反馈分散，忙碌时多个图标旋转 | 同一角框状态位跟随读取、审核、写入阶段；审核层接管反馈 | 减少重复运动，让结果有固定位置 |
| 请求成功、取消、部分配置与写入结果未知容易混淆 | 检查就绪中性、取消静态、部分完成警示、写入异常待核对；Excel 成功明确未保存 | 请求返回不等于全部配置或保存完成 |
| 小窗开启后，即使转去动画蓝图或其他应用仍轮询 | 默认识别前台窗口，其他/未知窗口停止新增 UE 自动读取 | 减少无关时段对编辑器的调用 |
| 暂停若卸载编辑器会丢失草稿，旧请求可能晚到 | 保留面板并 inert 锁定；丢弃晚到选择，恢复时重新确认节点 | 同时保留本地工作与当前选择约束 |
| NPC 位置编辑初始匹配在每次渲染重复计算 | 惰性初始化，仅组件首次挂载计算 | 去掉输入过程中不需要的重算 |

任务反馈复用 `TaskMotion` 和 `useOperationFeedback`，不增加任务调度或 UE 请求。
前台检测由独立 Win32 读窗口进程完成，不使用 UE Python、反射或向 UE 窗口发送消息。

## 请求量与检测边界

使用真实 App、前端请求 hook 与拦截 API 的固定响应，采样结果：

| 状态 | 时间窗口 | 新增选择请求 | 新增全部 UE 请求 |
| --- | --- | --- | --- |
| 对话编辑器被识别为活跃，节点不变 | 3.8 秒 | 3 | 未单独计数 |
| 切到其他窗口并确认暂停 | 3.8 秒 | 0 | 0 |

这证明暂停门控生效，不代表 UE 响应耗时、整机 CPU 或崩溃率改善百分比。
未使用生产资产读写来压测。原先稳定在线时 1.2 秒轮询对应约 50 次/分钟，
是由间隔推算的请求预算；实际频率还受响应耗时影响。

- 前台辅助进程每 400ms 采样，只在状态变化时通知前端；4 秒无心跳进入暂停。
  采样存在延迟，不能保证窗口刚切换的一瞬间没有请求。
- 原生只读短测中，当前非对话 UE 窗口被识别为未知并暂停；
  退出时辅助进程及 watchdog 正常清理，未留下该辅助进程。
- 隔离 Electron 窗口使用实际构建的前端和 preload、新辅助进程，以及模拟 API。
  自动暂停时选择请求为 0；关闭自动暂停后产生 1 次首读；IPC 开关、辅助进程关闭、
  窗口缩放和界面加载通过。隔离 userData 已清理，没有覆盖安装版配置。
- 暂停不撤销已经送到 UE 的执行，也不强行关闭正在使用的连接；
  空闲选择连接保留原来的 15 秒释放策略。恢复先排空旧选择请求，再发 `fresh=1` 首读。
- 老插件无法轻读真实 ID 时仍受 4.8 秒深读限频。重新进入或切换节点时，
  旧缓存不能作为有效新选择解锁编辑；可能短暂等待下一次有效读取。
- 标题规则仅认可 UE4Editor 的精确六位资产标题（可带 `*`）或明确对话编辑器标题。
  对话页签停靠后只显示工程名的情况无法可靠识别；可独立窗口或关闭自动暂停。
  尚未实测本机真实对话窗口的所有标题变体；此处保持保守暂停。

## 首轮记录的后续优化优先级

以下区分已证实的工作量与尚待耗时采样的候选，不把静态代码模式当成已测瓶颈。

| 优先级 | 工作量与证据 | 后续方向 | 本批状态 |
| --- | --- | --- | --- |
| 高：无关窗口中的 UE 读取 | `useUeDialogueSelection` 定时读取；旧插件会回退精确反射 | 按工作上下文暂停；后续插件提供可靠的选中节点 ID 与编辑器活动状态 | 前台暂停与恢复已实现；原生插件改造未做 |
| 中：轮询带动 App 重渲染 | hook 位于 `App`；每轮开始/结束更新 polling，即使节点内容相同也会驱动父组件更新 | 先采 React Profiler，考虑将读写灯与轮询状态下沉到局部组件，保留选择变化订阅 | 暂停时同时消除此工作量；活跃状态下尚未重构 |
| 中：大批目标物的派生数据 | `MissionTargetModal` 每次渲染多次 filter、创建 Set，行内再 find 槽位/目标物 | 对稳定快照建立 Map 与记忆化派生结果；用真实大列表测输入延迟后决定是否虚拟化 | 仅分析；没有全表规模基准，不宣称已有卡顿改善 |
| 中低：首次加载的 JS 解析 | 最终打包的 Vite 入口约 1,097.24 kB，gzip 332.14 kB；主 CSS 约 204.71 kB；StageView 约 209.16 kB，Three 模块约 350.25 kB | 测 Electron 冷启动，再沿依赖图拆出非首屏逻辑；不能只调大 warning 阈值 | 记录体积；未改拆包 |
| 按操作：UE/Excel 长耗时 | UE 多步审核/反射、Excel COM 跨进程调用受宿主响应影响 | 采集阶段耗时；优先批读与安全缓存，写入前继续实时校验；保持 COM 串行 | 原协议保留，没有用并发冒险换速度 |

已经存在的优化继续保留：`StageView` 活跃时 demand、后台 never；
小窗卸载 Canvas；CSV Worker 分块解析与数据库索引；动作目录/节点快照缓存；
动画配置扫描缓存。不能因为看到 3D 或长列表就认定它们在后台持续高负载。
本轮没有做长时间内存泄漏测试、UE 并行重负载帧率或冷启动时间测量。

后续本地打包验收补充了应用内“减少动态效果”设置。安装版默认关闭，不再因本机
Windows 动画偏好而默认进入静态模式；用户开启后立即停止循环扫描与页面位移并持久化。
浏览器开发环境没有应用偏好时仍沿用系统媒体查询，保留自动化和无障碍验证入口。

## 续作：活跃轮询、目标物列表与入口加载

本节为本轮源码与隔离验收结果，替代上表“尚未重构/仅分析/未改拆包”的状态。
没有再次覆盖安装、提升版本或发布。

| Before | After | Why |
| --- | --- | --- |
| 3.8 秒、3 次相同选择轮询引起 App 提交 6 次 | 同样 3 次请求，App 提交 0 次 | polling/退避间隔存入局部 external store，只有状态灯订阅；实际选择变化与首次验证仍通知编辑器 |
| 每次渲染重建目标物派生集合，逐行 find/findIndex | 稳定快照建立 Map/Set，未变化的表格行由 memo 复用 | 去掉二次扫描与查询输入引起的整表单元格重建，保持勾选、编号、UE 选择高亮 |
| 2,000 条合成列表，生产构建连续输入到下一帧中位耗时 191.9ms | 同样操作为 38.7ms | 两份构建使用同一夹具；8 次输入含首个 BP 变更导致的审核失效，不能当作整机或生产 UE 性能指标 |
| 入口 JS 1,096,770 字节，gzip 331,963 字节 | 708,991 字节，gzip 227,232 字节 | Three.js 从统一源模块树摇，操作时再加载导演编排、评估与精修；音频/动作/机位面板独立分包 |
| 独立“交互偏好”区与特殊开关 | “减少动态效果”以普通复选框与 UE 设置并排，默认关闭 | 与现有双列选项一致，消除空白单元格 |
| NPC 动作库下拉、删除、文件夹三个控件 | 一个文件夹按钮，原生多选后替换，取消不变 | 减少维护目录时的重复操作 |
| 搜索/读写按钮静态，多个位置可能同时等待 | 放大镜、读取箭头、笔按当前操作运动，状态条静态保留阶段 | 动效绑定真实请求；失败、结束、隐藏、减少动效时停止 |
| 小窗增加读取控制图标，顶栏内边距不同 | 原数据源图标控制暂停/恢复，右内边距统一 16px | 三个图标在完整窗口与 310px 小窗中保持相同右上角偏移 |

入口按最终落盘 JS 文件计量，减少 **35.4%**；入口无其他静态 JS imports。
这不是冷启动耗时降低 35.4% 的结论；3D 画面和具体操作仍会加载对应动态分包。
独立 Electron 演示场景中，把动态加载的 3D 也计入，初始画面 JS 总量为
1,659,296 → 1,603,176 字节（减少约 3.4%）；执行规则导演后累计为
1,664,019 → 1,619,904 字节。大部分 Three.js 体积被移到需要画面时加载，
因此入口下降幅度明显大于带 3D 画面的总量下降幅度。
生产列表测量与其他 UI 回归在同机运行，有调度噪声；开发构建的独立阶段记录为
索引实现后 153ms、行复用后 22.7ms，两组数据不混用为同一性能基准。
首次大列表挂载、切换 BP 后审核失效以及全选仍需处理实际变化，未做虚拟列表。
